# 扩展性基准（Scalability Bench）

`benchmarks/scalability_bench.py` 是 Mnemosis 的官方扩展性基准：一条命令
同时测出构建耗时、CPU 利用率、峰值内存、库大小、行数、冷/热查询延迟与
吞吐量，适合在任何机器上复现。

## 运行

```bash
# 10 万条（约 30 秒）
python benchmarks/scalability_bench.py --count 100000 --chunk 5000

# 100 万条（约 6 分钟，库约 5GB）
python benchmarks/scalability_bench.py --count 1000000 --chunk 5000

# 200 万条（约 13 分钟，库约 10GB）
python benchmarks/scalability_bench.py --count 2000000 --chunk 5000
```

结果以 JSON 打印到标准输出（不会写仓库文件）；脚本结束后自动清理临时
数据库。

## 指标说明

| 字段 | 含义 |
|---|---|
| `build_s` | 批量构建挂钟时间（秒） |
| `build_cpu_s` / `build_cpu_utilization` | 纯 CPU 时间与利用率。**以单核为基准**（1.0 = 用满 1 个逻辑核）；当前构建是单线程的 |
| `peak_rss_mb` / `peak_commit_mb` | 峰值物理内存 / 提交内存。Commit 是 Windows 概念；Linux/macOS 下 commit 字段为 0，此时以 RSS 为准 |
| `db_size_mb` | 构建完成后数据库文件大小 |
| `links_rows` / `terms_rows` | 关联边（无向规范行）与词条索引行数 |
| `app_cold_query_ms` | 全新打开引擎后的首次查询（应用级冷启动，OS 页缓存可能仍热） |
| `warm_query_p50/p95/p99_ms` | 预热后的查询延迟分位数（200 次采样） |
| `warm_query_qps` | 热查询吞吐量（查询/秒） |

## 参考数据

本机环境：Windows、Python 3.14、13th Gen Intel Core i9-13900H、64GB
内存、NVMe SSD（KINGSTON SNV2S2000G）、5000 分块。构建和冷查询强烈
依赖磁盘性能，换机器后数值会有明显差异。

| 规模 | 构建 | 库大小 | 峰值内存 | 冷首查 | 热查询 p99 |
|---|---|---|---|---|---|
| 10 万 | ~27s | ~543MB | ~620MB | ~2.8s | ~1.8ms |
| 100 万 | ~367s | ~5140MB | ~2021MB | ~28s | ~1.7ms |
| 200 万 | ~764s | ~9900MB | ~3500MB | — | ~1.7ms |

> 冷首查指应用冷启动后的首次查询：主要耗时在把索引从磁盘加载进内存
> （100 万条约 5GB），之后同一进程内的查询即为毫秒级热查询；不是每次
> 未命中缓存的查询都要 28 秒。

扩展趋势：构建时间复杂度约为 **O(N^1.1)**（数据量每翻一倍，耗时约增至
2.1 倍），峰值内存亚线性增长，热查询延迟稳定在毫秒级。冷查询主要由磁盘
读取决定（应用层冷启动，OS 页缓存可能仍热）。

数据说明：基准数据由固定种子生成的中文“用户购买记录”构成（用户、商品、
日期、价格随机），分布接近均匀；真实业务若存在严重数据倾斜（如长尾热词），
构建与查询指标会有浮动。

GC 说明：热查询采样期间已临时禁用 Python 垃圾回收（采样后恢复），p99
基本不含 GC 停顿；冷查询包含首次运行时的解释器初始化。

## 注意事项

- 内存底线：100 万条构建峰值约 2GB、200 万条约 3.5GB（含 200MB SQLite
  页缓存）；小内存机器请从小规模开始测。
- 磁盘预留：库文件约 5GB/百万条，构建期间临时排序还会占用临时目录空间；
  运行大规模基准前确认磁盘余量。
- `--chunk` 调优：默认 5000 是 10 万~200 万区间的较优点；低内存机器可以
  调小（如 2000），但构建会略慢。
- 冷查询是“应用级冷启动”，OS 页缓存可能仍热；要测纯磁盘冷启动需要先
  清页缓存（Windows 上较难，Linux 可用 `drop_caches`）。
